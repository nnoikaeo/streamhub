## ทำไมต้องทดสอบก่อน

ท่าฝัง Looker ปัจจุบันมีข้อจำกัดที่รู้แล้ว: รายงานที่แชร์แบบระบุบัญชี เปิดไม่ขึ้นบน Safari ทุกเครื่อง และรายงานที่แชร์แบบลิงก์ = URL หลุดแล้วคนนอกเปิดได้

Google Sheets **ไม่จำเป็นต้องรับข้อจำกัดชุดเดียวกัน** เพราะต่างจาก Looker ตรงที่มี read API ฝั่งเซิร์ฟเวอร์ ⇒ มีทางเลือกที่ Looker ไม่มี · แต่ละทางแลกคนละอย่าง และข้อที่ตัดสินผลลัพธ์ที่สุด (Google บล็อกการฝังไหม, สิทธิ์ propagate เร็วแค่ไหน, ชีตใหญ่ช้าแค่ไหน) **เดาจากเอกสารไม่ได้ ต้องยิงจริง**

## ทางเลือก 1 — iframe (ท่าเดียวกับ Looker)

เก็บท่าปัจจุบันไว้ทั้งหมด เปลี่ยนแค่ URL ที่ผนึกใน embed token

**หมายเหตุก่อนทดสอบ:** CSP ของเราเองบล็อก `docs.google.com` อยู่ ([securityHeaders.ts:33](../../server/middleware/securityHeaders.ts#L33)) ⇒ ถ้าไม่แก้ก่อน กรอบจะว่างเพราะ**เรา**บล็อก ไม่ใช่ Google บล็อก อย่าสรุปผิด · แก้ชั่วคราวบน branch spike เท่านั้น

| id | ทดสอบ | ผ่านเมื่อ |
|---|---|---|
| S1.1 | `curl -sI` ดู header ของ 4 URL ด้านล่าง หา `X-Frame-Options` / `frame-ancestors` | รู้แน่ว่า URL ไหนฝังได้ตามนโยบายของ Google เอง ก่อนเสียเวลากดใน UI |
| S1.2 | ฝัง `/preview` ของชีต **B** ใน Chrome ขณะล็อกอินบัญชีที่มีสิทธิ์ | เห็นข้อมูล |
| S1.3 | ทำ S1.2 ซ้ำบน **Safari macOS** | **นี่คือเคสชี้ขาด** — ถ้าไม่ขึ้น = อาการเดียวกับ BUG-032 เป๊ะ ทางเลือกนี้ตกทันทีสำหรับชีตที่ไม่ publish |
| S1.4 | ทำ S1.2 ซ้ำบน **iPhone Safari** | เทียบกับ S1.3 |
| S1.5 | ฝัง `/pubhtml?widget=true&headers=false` ของชีต **C** ทั้ง Chrome + Safari + iPhone | คาดว่าขึ้นครบทุกเครื่อง เพราะไม่ใช้คุกกี้เลย |
| S1.6 | เปิด URL ของชีต **C** ใน private window ที่ไม่ล็อกอิน | ยืนยัน C2 — คาดว่า**เปิดได้** = ข้อมูลสาธารณะจริง |
| S1.7 | ฝัง `/edit?rm=minimal&widget=true&headers=false` | ดูว่าได้ UI เนทีฟกว่า `/preview` ไหม และแก้ไขได้ไหม |
| S1.8 | ชีต **A** (ไม่มีสิทธิ์) ใน iframe | บันทึกข้อความ error ที่เห็น — ต้องแยกออกจากอาการคุกกี้ให้ได้ ไม่งั้นวินิจฉัยหน้างานไม่ได้ |
| S1.9 | ชีต **D** ใน iframe บนมือถือ | เลื่อน/ซูมใช้งานได้จริงไหมกับ 3,300 แถว |

URL ที่ต้องทดสอบใน S1.1:

```text
https://docs.google.com/spreadsheets/d/{id}/preview
https://docs.google.com/spreadsheets/d/{id}/edit?rm=minimal&widget=true&headers=false
https://docs.google.com/spreadsheets/d/{id}/pubhtml?widget=true&headers=false
https://docs.google.com/spreadsheets/d/{id}/gviz/tq?tqx=out:html
```

โค้ด spike ที่ต้องเขียน: แก้ `frame-src` + เพิ่ม pattern ใน [lookerUrl.ts](../../app/utils/lookerUrl.ts) + หน้า `/spike/sheets-iframe` ที่รับ URL แล้วฝังให้ดู (~0.5 วัน)

## ทางเลือก 2 — proxy อ่านผ่าน service account

เซิร์ฟเวอร์อ่านค่าเซลล์ด้วย service account แล้วเรนเดอร์เป็นตารางของแอปเอง ไม่มี iframe ไม่มีคุกกี้ Google

| id | ทดสอบ | ผ่านเมื่อ |
|---|---|---|
| S2.1 | เพิ่ม scope `spreadsheets.readonly` แล้วเรียก `spreadsheets.values.get` ชีต **B** | ได้ค่ากลับ — ยืนยันว่า "แชร์ให้ SA" พอแล้ว ไม่ต้องเป็นเจ้าของ (C3) |
| S2.2 | เรียกชีต **A** ที่ไม่ได้แชร์ให้ SA | ต้องได้ 403 — ยืนยันว่า SA ไม่ได้เห็นทุกอย่างในองค์กร |
| S2.3 | อ่านชีต **D** เต็มใบ จับเวลา + ขนาด payload | บันทึก ms และ KB · ช้ากว่า 3 วินาทีต้องออกแบบ paging |
| S2.4 | เรียกซ้ำ 20 ครั้งใน 1 นาที | ดูว่าชน quota ไหม (โควตาอ่านคิดรวมทั้งโปรเจกต์ ไม่ใช่ต่อ user) และต้อง cache ไหม |
| S2.5 | `spreadsheets.get?includeGridData=true` บนชีต **D** | ได้ format/สี/merge มาด้วยไหม และ payload บวมขึ้นเท่าไร — ตัวชี้ว่าจะทำ C4 ได้ใกล้แค่ไหน |
| S2.6 | ลอง `/export?format=csv&gid=N` พร้อม bearer token ของ SA | ถ้าได้ = ทางลัดที่เบากว่า API มาก บันทึกไว้ |
| S2.7 | เปิดหน้า spike บน **Safari + iPhone** | คาดว่าขึ้นปกติทั้งคู่ — ถ้าใช่ ทางนี้ปิดปัญหา C1 ได้จริง |
| S2.8 | ดูใน DevTools ว่า client เห็น URL/id ของชีตไหม | ต้องไม่เห็น ⇒ C2 = ไม่มีทางหลุด |
| S2.9 | ยิง endpoint ด้วย user ที่**ไม่มีสิทธิ์**ในแดชบอร์ดนั้น | ต้อง 403 จาก `checkDashboardAccess` ตัวเดียวกับ embed ไม่ใช่ตัวใหม่ |
| S2.10 | กรองแถวตาม `user.company` ก่อนส่งออก | พิสูจน์ว่าทำ row-level filter ได้ (สิ่งที่เข้าตรงทำไม่ได้) |
| S2.11 | ตรวจว่าเขียน audit ได้ระดับไหน | ยืนยัน C6 |

โค้ด spike ที่ต้องเขียน: `server/api/spike/sheet/[dashboardId].get.ts` + scope เพิ่ม + หน้าแสดงผลง่าย ๆ (~1.5 วัน)

## ทางเลือก 3 — ซิงก์สิทธิ์ลง Drive แล้วเปิดแท็บใหม่

StreamHub สั่ง Drive API เพิ่ม/ถอนอีเมลผู้ใช้บนชีตจริง แล้วให้ผู้ใช้เปิดในแท็บใหม่ (ไม่ใช่ iframe) — Google บังคับสิทธิ์เอง

⚠️ **ทางนี้เขียนสิทธิ์จริงบน Drive** ทดสอบกับชีตทิ้งขว้างเท่านั้น และตรวจสอบก่อนว่านโยบายของ Workspace อนุญาตให้ SA แชร์ออกนอกองค์กรไหม

| id | ทดสอบ | ผ่านเมื่อ |
|---|---|---|
| S3.1 | SA เป็นแค่ Viewer บนชีต แล้วสั่ง `permissions.create` | คาดว่า**ล้มเหลว** — ยืนยันว่าทางนี้ต้องมีสิทธิ์ Editor/เจ้าของ (C3 ข้อสำคัญที่สุด) |
| S3.2 | SA เป็นเจ้าของ/Editor แล้วสั่ง `permissions.create` role reader, `sendNotificationEmail: false` | ผู้ใช้เปิดได้ และ**ไม่มีอีเมลแจ้งเตือนไปหาเขา** |
| S3.3 | จับเวลาจากสั่งเพิ่มสิทธิ์ ⇒ เปิดได้จริง | บันทึกวินาที |
| S3.4 | `permissions.delete` แล้วจับเวลาจนเปิดไม่ได้ | **ช่องโหว่ของทางนี้อยู่ตรงนี้** — ถ้าถอนแล้วยังเปิดได้อีกหลายนาที ต้องรู้ว่ากี่นาที |
| S3.5 | เปิดชีตในแท็บใหม่บน **Safari + iPhone** | คาดว่าได้ครบ เพราะเป็น first-party ไม่ใช่ iframe |
| S3.6 | ผู้ใช้ที่อีเมล StreamHub **ไม่มีบัญชี Google** | บันทึกว่าเจอหน้าอะไร — เป็นข้อจำกัดถาวรของทางนี้ |
| S3.7 | ผู้ใช้เปิดชีตโดยไม่ผ่าน StreamHub (bookmark ตรง) | เปิดได้ ⇒ StreamHub ไม่ใช่ทางเดียว บันทึกเป็นสิ่งที่แลก |
| S3.8 | ลบผู้ใช้ใน StreamHub แล้วดูว่าสิทธิ์ Drive ถูกถอนไหม | ถ้าไม่ = ต้องเขียน cascade เพิ่ม เหมือน `folders.assignedModerators[]` |
| S3.9 | ฝังในแท็บใหม่ vs iframe เทียบกัน | ถ้า iframe ยังพังบน Safari ⇒ ทางนี้บังคับ "เปิดแท็บใหม่" ตลอด รับได้ไหม |

โค้ด spike ที่ต้องเขียน: `scripts/spike-drive-permissions.mjs` (grant/revoke/status พร้อม dry run แบบเดียวกับสคริปต์ QA ตัวอื่น) (~1 วัน)
